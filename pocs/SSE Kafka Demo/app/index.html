02 / Why SSE wins for this system

Half a protocol is a feature — when you only need half.

Our UI is a subscriber, not a peer. Every byte it needs flows server → client, and the bytes themselves are already shaped like the thing the UI was going to build anyway: Redux action payloads.

1

One-way is exactly right

The dashboard never pushes data back on this channel — writes and mutations go through normal REST with verbs, auth and retries. A WebSocket's bidirectionality (and its heartbeats, backpressure and message routing) would be dead weight we have to operate.

2

It's just HTTP

A normal GET with Accept: text/event-stream — so proxies, load balancers, auth headers and cookies all work unmodified. EventSource reconnects automatically and resumes with Last-Event-ID. No upgrade handshake, no framing layer, no ping/pong.

3

The payload IS the action

We don't ship a state snapshot and make the UI figure out what changed — the server already knows what changed. Frames carry { type, payload } deltas that map 1:1 onto action creators. The client's whole job is JSON.parse → dispatch.

The same updates. Three subscribers. Three different streams.

  updates per tick, tests each one against each subscriber's filter, and only writes frames that pass.
  Edit the criteria, then run the burst.

07 / One message, many updates

  
A Kafka record can carry a batch — and the batch survives the whole trip.

  
A single record holds an array of deltas; the aggregation window can merge in updates from
  other topics too. One SSE frame → many Redux dispatches in the same tick → one consistent UI paint.
  Same controls — step it and watch the frame contents grow in the inspector.

The takeaway: batching is preserved end-to-end — one transaction becomes
      one record, one MULTI, one publish, one SSE frame, one tick of dispatches, one paint. Atomicity is
      never lost in transit; and per-delta filtering still applies, so a mixed frame can shrink but never tear.

08 / The client: hook → store → selectors

  
One connection in. Selective re-renders out.

  
The provider parses each frame, maps deltas to actions, and dispatches. Components
  useSelector only re-render when their selected value changes;
  the event bus carries the side-effect subset. Send frames and watch the render meters — code highlights run in sync.

11 / Recap

  
Six things to remember when you build this.

  

    
1
One canonical envelope

      
Every topic normalizes to { type, payload, ts, origin }. Downstream code never cares which topic an update came from — that's what makes N→1 fan-in cheap.

    
2
Redis is the rendezvous

      
Kafka consumers write; SSE workers read. One Redis DB decouples ingest rate from fan-out rate and gives late joiners current state, not just the live tail.

    
3
Filter on the server, not the client

      
Subscriber criteria live in the gateway. A phone on 4G never pays the bandwidth for updates it would have thrown away anyway.

    
4
Array frames = atomic batches

      
A multi-delta Kafka record becomes one SSE frame. All its dispatches land in the same tick, so the UI never paints a half-applied batch.

    
5
Two lanes on the client

      
dispatch feeds the store (state); the event bus feeds side effects (toasts, flashes). State subscribers and event listeners evolve independently.

    
6
useSelector is the last filter

      
Even after the server's filter, components re-render only when their selected slice changes. Filtering happens at every layer — bandwidth, frames, dispatches, renders.
